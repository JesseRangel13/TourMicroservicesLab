## Changes and confirmed defects

1. `src/Shared.Infrastructure/LabHosting.cs`: human JWT authentication previously accepted cryptographically valid tokens with missing/ambiguous identity claims and did not enforce the declared fifteen-minute maximum. It now requires one nonblank bounded subject, supported unique Tourist/Admin roles and a bounded not-before/expiration interval, in addition to existing RS256/key/issuer/audience/lifetime checks. All human service policies use this validator with explicit bearer schemes. Expected malformed-token failures disclose no token details.
2. `src/Catalog.Api/CatalogEndpoints.cs`: the dedicated Reservations scheme additionally rejects ambiguous subjects and multiple permission claims. It remains restricted to the internal quote policy, original dedicated key, exact subject/permission and two-minute lifetime. Wrong authenticated service permission/subject yields 403; invalid trust/identity yields 401. Human tokens cannot substitute. Gateway literal route blocking passes methods/case/encoded segment checks without a new permissive proxy transformation.
3. `src/Gateway.Web/Components/Pages/Operations.razor` and `TourProjections.razor` previously had button handlers but no Interactive Server render mode. Routes/App are static shells, so these controls were static HTML. Both now explicitly opt into Interactive Server. SSR regression checks assert the server component marker; real browser clicks remain NOT VERIFIED. This is a confirmed defect found beyond LAB-006's SSR review boundary, not a claim that the earlier review executed clicks.
4. Progress polling could continue after authentication/request errors, and some detail pages retained the previous resource while loading another ID. `Payments.razor`, `Notifications.razor`, `ReservationDetail.razor` and `Sagas.razor` clear parameter-bound data, stop polling on errors/terminal state and restart after successful explicit reload/recovery. Owned polling tasks are cancelled/joined on disposal. `CatalogComponent.cs` makes disposal idempotent and rejects queued actions after disposal.
5. The first expired-cookie test confirmed rejection but found a 302 login redirect at `/auth/me`, contrary to the API's 401 convention. `IdentityRegistration.cs` now sends 401 for this identity API while preserving normal HTML login redirects. The strengthened fixture proves a valid ticket from the real encrypted durable key ring works before proving the expired ticket is rejected.
6. Verification RSA instances were supplied as externally created singleton objects, leaving disposal outside DI ownership. Named JwtBearer Options now resolve factory-created DI-owned verification resources. Gateway disposes its Data Protection certificate at application stop. Identity contexts remain in short HTTP/tool/revalidation scopes; no circuit DbContext was added.
7. Credential inputs are bounded server-side; login/token responses retain private behavior, token responses are no-store, and framework request/token diagnostics are filtered to avoid verbose credential/query/token logging. No password/key/token was versioned. Existing antiforgery, TLS, secure Strict cookies, stamp revalidation, per-request JWTs, API ownership/Admin policies and intention keys were preserved.
8. Updated current navigation/stage text, security instructions, endpoint/control inventory, actual seventeen-topic learning map, runnable pinned browser tests, demo guide and consolidated acceptance matrix. No extra service/project/infrastructure layer, domain transaction redesign, paid resource or cloud deployment was introduced.

The explicit API-tool `/auth/token` versus no-secrets-in-UI interpretation is documented in `docs/security-execution.md`: Blazor covers credential sign-in/identity inspection; the specified JSON API-tool issuer is not turned into a browser token export/storage feature. No endpoint issues tokens by choosing a name/role. No change to money/inventory transitions was needed.
